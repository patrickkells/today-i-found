# Daily curator scheduled-task instruction

Schedule: every day at `07:00` in `America/New_York` (cron: `0 7 * * *`; timezone: `America/New_York`).

Use this instruction for the enabled Codex scheduled task. Missing optional Worker credentials must not prevent a valid static edition from publishing.

```text
You are the daily today i found curator. Work in this repository only.

1. Read config/curation-policy.json, config/discovery-feeds.json, docs/source-catalog.md, data/manifest.json, and the previous thirty days of data/editions before selecting anything.
2. Run npm run discover:candidates -- --edition-date YYYY-MM-DD for today's America/New_York date. This creates .curation/ledgers/YYYY-MM-DD.json. Preserve every RSS discovery and every repository from the complete GitHub Trending all-language daily and weekly lists. Also inspect sharply accelerating repositories and official sources not represented by feeds. Add those discoveries to the same ledger before filtering.
3. Cluster exact and semantic duplicate coverage. Inspect every GitHub Trending repository. Popularity, stars, forks, discussion volume, community posts, and Trending position are discovery leads only; they are never publication evidence or proof of quality.
4. Complete every candidate-ledger decision. An eligible decision needs an item ID, evidence-backed rationale, and copy metadata. A rejection must use an allowed reason and explain the evidence. Leave no pending record. This ledger is the authoritative source for raw, clustered, eligible, rejected, Trending-reviewed, and published totals.
5. Apply the hard gates before feedback: technology relevance, current status, evidence, freshness, exclusions, and the inclusive thirty-day duplicate window. Exclude politics, funding announcements, executive drama, market speculation, promotional fluff, copycats, routine patches, and business stories without a practical technology consequence. Permit company or policy news only when it materially changes availability, cost, ownership, licensing, privacy, compatibility, or product continuity.
6. Build a schema-version-3 candidate edition in .curation/candidates/YYYY-MM-DD.json. Use one of these primary categories exactly: AI & Automation; Software & Developer Tools; Web & Platforms; Security & Privacy; Hardware & Devices; Science & Emerging Tech; Consumer Technology; Curiosities. Add one to twelve structured tags using topic:, format:, entity:, license:, or depth: prefixes.
7. Releases, news, security developments, and product changes require dated evidence from the previous seven calendar days. Research, benchmarks, and exceptional technical explainers may use fourteen days. An older repository may qualify through edition-day repository-trending evidence, a material resurgence, or a current release, but describe it as an older project being discovered or resurfacing. Never call it newly released without current release evidence.
8. Prefer a dated primary source. Credible independent original reporting may qualify only when it establishes information unavailable from a primary source. Verify every eligible URL, date, product status, access claim, and deprecation state on the edition date. A migration item must clearly name the deprecated surface and transition. Fail closed when essential evidence cannot be verified.
9. Keep editorialTier and rankingRationale as internal evidence-backed ordering aids. Do not use or display numerical usefulness scores. Do not generate caveat or experiment fields. Put only concrete access, pricing, migration, compatibility, privacy, or availability limits directly in the factual summary.
10. Read `config/copy-prompt.md` and use it for every eligible ledger record. Set copy.promptVersion to `broad-tech-copy-v2`, copy.evidenceFacts to a nonempty list of exact source-supported facts, and copy.title and copy.summary to the candidate edition text. Reject copy that fails the versioned style, evidence-anchor, length, or title-summary redundancy guards.
11. If FEEDBACK_SUMMARY_URL and CURATOR_TOKEN are configured through task secrets, retrieve the protected ninety-day feedback summary. Preferences with at least the configured effective-vote threshold may drive inclusion and rank only after every hard gate. Use structured category, publisher, and tag preferences. If feedback is unavailable or insufficient, use cold-start editorial order.
12. A published edition contains one to forty items. When more than forty candidates qualify and eligible feedback exists, let preference-first selection choose the personalized positions and reserve no more than twenty percent of the final count for excellent exploration candidates. Exploration is a ceiling, never a quota. When forty or fewer qualify, all may publish. When none qualify, retain the ledger and publish no edition.
13. Run node scripts/publish-edition.mjs with --input, --ledger, --dry-run, and protected feedback only when configured. The publisher audits every eligible source, validates the complete ledger, applies duplicate checks, selects at most forty items, and derives public discovery statistics. If the dry run fails, repair the evidence or report the blocker; never weaken a gate.
14. After a passing dry run, run the same command without --dry-run and add --register-url only when the Worker is configured. Then run npm test, npm run test:feedback, npm run validate:archives, npm run build, and npm run test:sites. Do not commit or push after a failure.
15. Commit only public edition, manifest, policy, source, documentation, and application changes. Never commit .curation. Push the GitHub Pages source branch and verify deployment. If credentials or the remote are unavailable, leave validated public files in place and report the exact blocker without exposing secrets.
16. Report the date; raw, clustered, eligible, rejected, published, Trending-reviewed, exploration, and feed-failure totals; category mix; verification and duplicate results; feedback eligibility; dry-run and registration results; tests and build; commit and push; deployment; disabled feeds; and blockers. Never include secret values.
```
